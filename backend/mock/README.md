# Мок-бекенд Vendo (Node + Express, in-memory)

Демонстраційна реалізація **єдиного REST-контракту** для локальної розробки, демо-стенду
й тесту фронтенду — без 1С. Дані — із фікстури `data/db.json`, працюють у пам'яті.
Справжній бекенд — 1С HTTP-сервіс (`../1c-config/TradeUkr23/`).

## Запуск

```bash
npm install
npm start          # http://localhost:3000, базовий шлях /api
```

- Swagger UI контракту: http://localhost:3000/api/docs (спека — `openapi.json`).
- Адмінка стенду: http://localhost:3000/admin (лише з локальної машини, див. нижче).
- Немає watch/reload — після правок перезапусти вручну (`require` кешує модулі).
- Жодних нативних модулів/збірки — чистий Node (`express` + `cors`).

## Тести

```bash
npm test           # node --test (без залежностей)
```

Покривають чисті хелпери (`lib/orders.js`, `lib/devices.js`), сумісність контракту
(`contract.test.mjs`) і гейт пристрою по HTTP (`routes/api.test.mjs`: прив'язка,
блокування, фільтрація за пристроєм). Тести піднімають express на ефемерному порту й
виставляють `VENDO_NO_PERSIST=1`, щоб не лишати `db.state.json`.

## Дані

- `data/db.json` — **еталонний сід**, у git; у рантаймі не переписується.
- `data/db.state.json` — робочий стан (у `.gitignore`): пишеться після кожної мутації
  (замовлення з додатка, правки в адмінці, телеметрія, прив'язки) і читається при старті
  замість сіду. У консолі при старті видно, звідки прочитано.
- Повернутись до сіду — кнопка **«Завантажити дані за замовчуванням»** в адмінці
  (або просто видалити `db.state.json`).

## Адмінка (`/admin`)

Одна сторінка без збірки; дзеркалить те, що оператор робить у 1С у довіднику
`венд_МобильныеУстройства`:

- **Пристрої** — картка (склад, валюта, менеджер, глибина історії, режим обробки
  замовлення, блокування), генерація коду прив'язки й QR у тому ж форматі, що читає
  застосунок, списки доступу (контрагенти / товари / типи цін). Товари й контрагенти —
  **дерева**: можна позначити як окремий елемент, так і категорію/папку, і тоді доступне
  все, що під нею (узагальнене посилання + `В ИЕРАРХИИ`, як у 1С).
- **Телеметрія** — останній стан пристроїв, історія снапшотів, перегляд надісланого
  логу, кнопка «Запросити лог».
- **Демо-дані** — перегляд і правка товарів, контрагентів, категорій, замовлень і
  простих таблиць (склади / валюти / менеджери). Список читальний і на всю висоту вікна,
  редагування — у модальному вікні по кліку на рядок; вкладені масиви (позиції замовлення,
  контактні особи) правляться там своєю таблицею, а не JSON-ом.
- **Налаштування стенду** — інтервали циклів додатка (`/health`), `minAppVersion`,
  валюта, глибина історії, строк зберігання телеметрії.

**Доступ.** Стенд публікується тунелем назовні, тому адмінка й `/admin/api` відповідають
лише на локальні запити: локальна адреса сокета + `Host: localhost` + відсутність
`X-Forwarded-*` (одного лише IP замало — `ssh -R` приносить запити з тунелю теж із
127.0.0.1). Виняток для стенду на віддаленій машині — `ADMIN_ALLOW_REMOTE=1`.

## Ендпоінти

| Метод | Шлях | Опис |
|---|---|---|
| `GET`/`HEAD` | `/health` | дешева перевірка доступності + інтервали циклів (без авторизації) |
| `POST` | `/auth` | обмін одноразового коду прив'язки на токен (без авторизації) |
| `GET` | `/products` | номенклатура пристрою (ціни за доступними типами, залишок, штрихкод, фото) |
| `GET` | `/products/{id}/image` | завжди 404 (демо не зберігає бінарних фото — як 1С без зображення) |
| `GET` | `/categories` | категорії (дерево, `parentId`) |
| `GET` | `/customer-groups` | папки контрагентів |
| `GET` | `/price-types` | типи цін, доступні пристрою |
| `GET` | `/customers` | контрагенти (адреса/телефон/контактні особи/борг) |
| `GET` | `/customers/{id}/ordered-products` | GUID товарів, які контрагент замовляв |
| `GET` | `/orders?startDate=&endDate=` | замовлення за період (у межах глибини історії) |
| `POST` | `/orders` | upsert за клієнтським GUID (ідемпотентно; конфлікт версій → 409) |
| `PUT` | `/orders/{id}` | оновити замовлення (за GUID) |
| `DELETE` | `/orders/{id}` | «Нове» — видалити; інше — помітка на видалення |
| `POST` | `/telemetry` | снапшот стану пристрою (лягає в історію) |

Усе, крім `/health` і `/auth`, вимагає спареного незаблокованого пристрою:
`X-Device-Id` + `X-Auth-Token`; інакше — `401` (додаток за цим сигналом виходить на
екран входу).

## Чим відрізняється від 1С

Мок реалізує **той самий контракт**; відмінності — у джерелі даних, не в поведінці:

- дані беруться з фікстури, а не з документів і регістрів УТ (немає проведення,
  реалізацій, курсів валют — конверсія цін імітується фіксованими курсами);
- склад / валюта / менеджер — прості таблиці стенду, а не довідники УТ;
- **порожній список доступу = без обмеження** (у 1С порожня ТЧ дає порожній результат:
  там списки заповнює оператор при заведенні картки, а тут свіжий пристрій, який не
  бачить нічого, читався б як зламаний стенд). Назовні, у контракті, це не видно.

## Контракт

Канон — [`openapi.json`](openapi.json) (Swagger на `/api/docs`). Замовлення зберігаються
**нормалізовано** (посилання на товар/контрагента + зафіксована ціна per-рядок — snapshot
на момент замовлення), а на віддачі **гідратуються** (`hydrateOrder` добудовує
`customer`/`items[].product`/`total`). Номери — з лічильника (`ЗМ-N`, не повторюються).
Оптимістична конкуренція — токен `version` (як `ВерсияДанных` у 1С): редагування від
застарілої версії → `409`. Будь-яка інша реалізація контракту (зокрема 1С) сумісна без змін.
